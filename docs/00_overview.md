# Косметическая накладка голени — параметрическая модель на Geometry Nodes

Проект: параметрическая 3D-печатная косметическая накладка на протез
голени. Строится **полностью на geometry nodes** в Blender (целевая
версия — 5.1; скрипты разрабатывались и проверялись на Blender 4.0,
см. «Совместимость» ниже), без фото/3D-сканов — по вводимым числовым
параметрам (длина сегмента, обхваты и т.д.), с диапазонами средних
анатомических значений взрослого человека на первом этапе.

Печать: Elegoo Centauri Carbon, филамент PETG.

## Как устроен проект

Работа разбита на логические группы узлов (по ТЗ):

1. **Ось** (`NK.1_Ось`) — вертикальная кривая-хребет от лодыжки до
   колена, с наклонами и задним прогибом на уровне икры. **Готово.**
2. **Профиль** (`NK.2_Профиль`) — переменное поперечное сечение
   голени вдоль оси: обхваты в 2 точках, уплощение большеберцовой
   кости (гребень спереди), округлость икроножной мышцы сзади.
   **Готово.**
3. **Оболочка** (`NK.3_Оболочка`) — лофт профилей вдоль оси в 3D-меш,
   подрезка сверху/снизу, разделение на переднюю/заднюю половины.
   **Готово.**
4. **Рассечение под принтер** (`NK.5_Печать`) — разбиение деталей по
   габаритам стола принтера, подбор угла для печати. **Готово.**

**Правки 220926:** из проекта полностью удалены (1) Группа 4
«Закладные» (хомуты/винты/гайки М3, посадочные места под магниты) и
(2) ВСЕ узлы пазового/шпунтового соединения деталей — как фальц
(«четверть») между Перед/Зад в Группе 3, так и паз/шип между
Верх/Низ в Группе 5. Нумерация групп (`NK.1`..`NK.5`) в именах
node-групп в коде оставлена как есть (не переименовывалась при
удалении Группы 4), поэтому счёт теперь 1→2→3→5 (Группы `NK.4_*` в
проекте больше нет). Половины/сегменты сшиваются по прежней геометрии
шва БЕЗ какого-либо интерлока — просто номинальная (не утопленная,
без паза) поверхность стыка. Подробности и мотивация — см.
"Резюме сессии" (готовится отдельным файлом) и историю коммитов.

Полная цепочка 1→2→3→5 автоматически проверена
(`scripts/verify_group5.py`) и даёт до 4 STL-готовых сегментов
(Перед_Низ/Верх, Зад_Низ/Верх) с корректной замкнутостью и
ориентацией нормалей на каждом шаге — после удаления пазов ВСЕ 4
тестовых кейса проходят строгую проверку `Провер_ВСЕ_OK`=True с 0
незамкнутых рёбер (раньше, с пазами, часть кейсов "честно" не
проходила эту проверку из-за остаточных Boolean-дефектов на пазах —
см. историю коммитов).

Каждая группа — это **отдельная Geometry Nodes группа** (node group),
которую можно как открыть отдельно, так и подключить узлом `Group`
(`GeometryNodeGroup`) в общее дерево `NK.Master`. Так группы можно
разрабатывать, проверять и версионировать по отдельности — именно
поэтому после каждой группы обязательна проверка (см. ниже).

## Единицы измерения — читать перед началом работы

Все размеры в проекте — это **сырые числа = миллиметры**. Мы **не**
используем метры Blender по умолчанию. То есть длина `350` в узле
значит "350 мм", а не "350 м".

Почему так: избегаем путаницы масштаба (1 юнит Blender = 1 мм —
стандартная практика для 3D-печати), и STL/3MF-экспорт для слайсера
Elegoo (Chitubox/Orca и т.п.) получает числа сразу в миллиметрах при
масштабе экспорта = 1.

В сцене выставлено: `Единицы → Метрическая`, `Масштаб единиц = 0.001`
— это влияет только на то, как Blender **подписывает** линейку/панели
(будет показывать "350 мм" вместо "350 м"), но не меняет сами
координаты. Если вы создаёте новые сцены/объекты вручную — не
забудьте выставить это же в Scene Properties → Units.

## Система координат (одна на все 5 групп)

```
      Z (вверх, к колену)
      |
      |
      +----- Y (вперёд, "перёд" голени / гребень большеберцовой кости)
     /
    X (наружу/латерально)
```

- **X** — медиально-латеральная ось. `+X` = латерально (наружу).
- **Y** — сагиттальная ось. `+Y` = вперёд (передняя поверхность,
  гребень большеберцовой кости). `-Y` = назад (задняя поверхность,
  где расположена икроножная мышца).
- **Z** — вертикальная ось. `+Z` = вверх, к колену.
- Начало координат `(0,0,0)` = **точка A**, дистальный конец сегмента
  (уровень лодыжки / стыка со стопой).

Эта конвенция задана в Группе 1 и должна использоваться без изменений
во всех последующих группах — иначе профили (Группа 2) "приедут" не
той стороной.

**Левая/правая нога:** всё построено для условной "правой" ноги (икра
и гребень смотрят как для правой). Для левой ноги на последнем этапе
(перед печатью) достаточно зеркально отразить готовую деталь по оси X
(`Transform` со Scale X = -1, либо просто зеркалим STL в слайсере).

## Диапазоны параметров (средние анатомические значения)

На первом этапе берём усреднённые значения взрослого человека; каждый
параметр — с адекватным диапазоном, чтобы им можно было пользоваться
и для других людей в будущем (согласно ТЗ, п.5):

| Параметр | По умолчанию | Диапазон | Источник/логика |
|---|---|---|---|
| Длина сегмента (лодыжка→колено) | 350 мм | 150–500 мм | средний рост голени взрослого 300–400 мм с запасом |
| Наклон сагиттальный | 0° | −10…+10° | коррекция под гильзу/модуль |
| Наклон фронтальный | 0° | −10…+10° | коррекция варус/вальгус |
| Высота макс. обхвата икры (от колена) | 0.30 (30%) | 0.10–0.60 | икра максимальна в верхней трети голени |
| Прогиб оси назад на уровне икры | 15 мм | 0–40 мм | видимый прогиб хребта, не путать с полным профилем мышцы (Группа 2) |

Диапазоны будут уточняться в Группе 2 добавлением самих обхватов.

## Совместимость версий Blender

**Обновление: весь проект реально пересобран и проверен на настоящем
Blender 5.1.2** (не только "должен работать" — граф был прогнан через
headless 5.1.2 и потребовал реальных правок API, см. ниже). Blender
4.0.2 (Ubuntu-пакет) остаётся установленным в среде и по-прежнему
собирает те же графы без ошибок (обратная совместимость сохранена),
но 5.1.2 — актуальная целевая и проверочная версия.

**Как здесь получен настоящий Blender 5.1, если `blender.org` в этой
песочнице недоступен:** сетевая политика этого окружения блокирует
прямые загрузки с `blender.org`, но у Blender Foundation есть
официальный pip-пакет `bpy` (PyPI не блокируется) — это ПОЛНОЦЕННЫЙ
Blender, собранный как импортируемый Python-модуль, без отдельного
GUI-бинарника. Для Python 3.13 (`cp313`) на PyPI доступны колёса
`bpy==5.1.0/5.1.1/5.1.2` (и даже 5.2.x). Установлено так:

```bash
python3.13 -m venv /opt/bpy51venv
/opt/bpy51venv/bin/pip install bpy==5.1.2
```

и запускается не как `blender --background --python script.py -- args`,
а напрямую интерпретатором той venv:

```bash
/opt/bpy51venv/bin/python3 scripts/verify_group1.py -- builds/
```

(Скрипты сами по себе не изменились — они как искали `--` в `sys.argv`
для аргументов, так и ищут; работает при обоих способах запуска.)
Рендер (`BLENDER_WORKBENCH`) и сохранение `.blend` в этом pip-режиме
тоже работают (с теми же безобидными EGL-предупреждениями и
автоматическим fallback на surfaceless-рендер, что и в обычном
headless `blender --background`).

### Реальные различия API между 4.0.2 и 5.1.2, найденные и исправленные

При первом прогоне на 5.1.2 обнаружились не косметические, а
поведенческие изменения - все исправлены ЦЕНТРАЛИЗОВАННО в
`scripts/nodes_common.py` (`add_node`/`in_sock`/`out_sock`), а не по
каждому отдельному месту кода, поэтому ни один `build_group*.py` файл
менять не пришлось:

1. **Часть "mode"-подобных СВОЙСТВ узла мигрировали на ВХОДНЫЕ СОКЕТЫ
   типа MENU.** Например, `GeometryNodeResampleCurve.mode` и
   `GeometryNodeFilletCurve.mode` в 4.0 были обычными свойствами
   (`n.mode = 'COUNT'`), а в 5.1 это отдельный сокет `"Mode"` со своим
   `default_value`. `add_node()` теперь сам ловит `AttributeError` при
   `setattr` и ищет подходящий MENU-сокет как запасной вариант.
2. **Строковые значения самих enum'ов на MENU-сокетах тоже
   переписаны** под человекочитаемый вид: было `'NGONS'` → стало
   `'N-gons'`, было `'COUNT'` → `'Count'` (плюс появился новый пункт
   `'Evaluated'`, которого не было в 4.0). `add_node()` при неудаче
   точного совпадения парсит реальный список допустимых значений прямо
   из текста ошибки Blender (RNA не даёт их статически для MENU) и
   сопоставляет без учёта регистра/пробелов/дефисов.
3. **Типизированные идентификаторы сокетов УНИФИЦИРОВАНЫ.** В 4.0 узлы
   вроде `Store Named Attribute` (`Value_Float`/`Value_Vector`/...),
   `Sample Index` (`Value_Vector`) и особенно `Switch`
   (`True_006`/`False_006`/`Output_006`/`Switch_001` - специфика была
   задокументирована как отдельная "грабля" в самом начале проекта)
   давали разный `identifier` сокета в зависимости от типа данных. В
   5.1 все они унифицированы до простого базового имени без суффикса
   (`Value`, `True`, `False`, `Output`, `Switch`) - для ЛЮБОГО типа
   данных один и тот же identifier. `in_sock()`/`out_sock()` теперь
   при неудачном точном совпадении пробуют часть identifier'а до
   первого `_` как запасной вариант - старый код 4.0-эры (написанный
   с суффиксами) продолжает работать без изменений.
4. **Самое важное - `GeometryNodeMeshBoolean.solver` сменил умолчание
   с `'EXACT'` (4.0) на `'FLOAT'` (5.1).** Весь этот проект вручную
   вытюнен и вычитан под конкретное поведение именно EXACT-решателя
   (десятки комментариев по всему коду про "точный Boolean-решатель").
   На умолчательном FLOAT-решателе число "дырявых" граничных рёбер в
   Группе 4 выросло примерно **в 5 раз** на идентичных параметрах
   (пример: 227/398 → 1124/1333 на кейсе `default`) - это не деградация
   кода, а просто менее надёжный решатель по умолчанию. Исправлено:
   `add_node()` теперь ВСЕГДА принудительно выставляет
   `solver='EXACT'` на любом новом `GeometryNodeMeshBoolean`, если явно
   не передан другой `solver=` - после этого числа дефектов почти
   совпали с 4.0.2 (то же самое: 292/531 на `big_magnets`, 43/88 на
   `short_cover`, 0/264 на `no_rib` - совпадение до последней цифры).

Все проверочные скрипты (`verify_group1..5.py`) прогнаны на 5.1.2
заново после этих правок и дают результаты, совпадающие (или очень
близкие) с задокументированными для 4.0.2 - см. таблицы результатов в
`docs/0N_*.md`.

## Как собрать/пересобрать проект локально

Каждая группа — это Python-скрипт в `scripts/`, который **с нуля**
строит соответствующую node group через `bpy`. Скрипты идемпотентны:
повторный запуск полностью пересобирает группу (старая версия
удаляется), поэтому можно спокойно менять код и запускать заново.

```bash
# сборка + автоматическая проверка + рендер превью + сохранение .blend

# вариант A: обычная установка Blender (любая ОС, GUI+CLI)
blender --background --python scripts/verify_group1.py -- builds/

# вариант B: только pip-пакет bpy (см. "Совместимость версий" выше) -
# именно так проверялось в этой headless-песочнице на версии 5.1.2
/opt/bpy51venv/bin/python3 scripts/verify_group1.py -- builds/
```

Готовый файл для открытия руками (без консоли): `builds/group1_axis.blend`.

## Проверка работоспособности — как это устроено

У каждой группы узлов внутри дерева есть отдельная секция
**"ПРОВЕРКИ"** (узлы с префиксом `V<номер_группы>.<номер>`, например
`V1.1`…`V1.9`). Это обычные geometry-nodes узлы (`Compare`,
`Boolean Math`, `Attribute Domain Size`, `Bounding Box`), которые
сравнивают то, что фактически получилось, с тем, что должно было
получиться, и выводят на выход группы:

- `Провер_ВСЕ_OK` (булево) — общий вердикт по группе;
- `Провер_Отчёт` (строка) — короткая расшифровка чисел.

**Как посмотреть значение в Blender (для не-программиста):**
1. Откройте `Spreadsheet` (Таблица) редактор снизу вьюпорта (или
   смените один из редакторов на него через иконку слева-сверху).
2. Выберите объект с модификатором Geometry Nodes.
3. В модификаторе, в самом низу панели "Output" (Свойства → Модификаторы),
   у каждого небулево/нестрокового выхода есть маленькое текстовое поле
   "Output attribute" — впишите туда любое имя (например `ok`), и
   значение появится колонкой в Spreadsheet на нужном домене
   (Point/Curve).
4. Либо проще: подключите `Провер_ВСЕ_OK` к `Viewer` узлу
   (`Ctrl+Shift+ЛКМ` по узлу) — тогда его значение сразу видно и во
   вьюпорте, и в Spreadsheet без ручного ввода имени атрибута.

Дополнительно, при разработке каждая группа прогоняется через
headless-скрипт `verify_group*.py`, который **автоматически** печатает
результат проверок для нескольких комбинаций параметров (умолчания,
крайние значения) и рендерит превью формы — так вы получаете и
числовое, и визуальное подтверждение прямо в чате, без необходимости
самому открывать Blender на этом этапе.
